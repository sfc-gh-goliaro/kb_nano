import triton

@triton.jit
def add_kernel(
    x_ptr,  # Pointer to first input
    y_ptr,  # Pointer to second input
    out_ptr,  # Pointer to output
    n_elements,  # Total number of elements in input/output
    BLOCK_SIZE: tl.constexpr,
):
    # Each program handles a contiguous block of data of size BLOCK_SIZE
    block_start = tl.program_id(0) * BLOCK_SIZE
    # Create a range of offsets [0..BLOCK_SIZE-1]
    offsets = block_start + tl.arange(0, BLOCK_SIZE)
    # Mask to ensure we don't go out of bounds
    mask = offsets < n_elements
    # Load input values
    x = tl.load(x_ptr + offsets, mask=mask, other=0.0)
    y = tl.load(y_ptr + offsets, mask=mask, other=0.0)
    # Perform the elementwise addition
    out = x + y
    # Store the result
    tl.store(out_ptr + offsets, out, mask=mask)


def triton_add(x: torch.Tensor, y: torch.Tensor):
    """
    This function wraps the Triton kernel call. It:
      1. Ensures the inputs are contiguous on GPU.
      2. Calculates the grid (blocks) needed.
      3. Launches the Triton kernel.
    """
    assert x.is_cuda and y.is_cuda, "Tensors must be on CUDA."
    x = x.contiguous()
    y = y.contiguous()

    # Prepare output tensor
    out = torch.empty_like(x)

    # Number of elements in the tensor
    n_elements = x.numel()
    BLOCK_SIZE = 128  # Tunable parameter for block size

    # Determine the number of blocks needed
    grid = lambda meta: ((n_elements + meta["BLOCK_SIZE"] - 1) // meta["BLOCK_SIZE"],)

    # Launch the Triton kernel
    add_kernel[grid](x, y, out, n_elements, BLOCK_SIZE=BLOCK_SIZE)
    return out

1) What the original PyTorch code does

- It implements a simplified MBConv-like block:
  - Optional 1x1 expand convolution: in_channels -> in_channels * expand_ratio
  - Depthwise convolution: kernel_size x kernel_size, stride, padding=(kernel_size-1)//2, groups=hidden_dim (i.e., each input channel is convolved separately)
  - 1x1 project convolution: hidden_dim -> out_channels
  - A residual add if stride == 1 and in_channels == out_channels

- Each convolution is followed by BatchNorm and ReLU6 in the original code. Note: That order (Conv -> BN -> ReLU6) is atypical; typical is (Conv+Bias) -> ReLU6 -> BN or BN fused into conv in inference. But we will preserve the semantics.

2) Where the time goes

- The dominant cost is the three convolutions (two 1x1 and one depthwise 3x3/5x5).
- On CUDA, PyTorch uses highly optimized cuDNN kernels which are already very fast. Writing custom Triton kernels can match or sometimes beat them for specific shapes, but it’s non-trivial.

3) What is feasible and realistic to optimize with Triton here

- Full 2D convolution (especially depthwise) in Triton is complex and lengthy. A correct, high-performance implementation would need careful tiling, vectorization, shared memory usage, and likely multiple kernels or fusion.
- A more practical first step is to optimize the elementwise parts (ReLU6 and potential final residual add) with Triton. These are memory-bandwidth bound and simple to implement correctly and safely.
- We can also write a custom 1x1 convolution kernel (which is essentially a per-position GEMM: C[H,W] = A[in_c, H, W] @ B[in_c], but with broadcasting over H,W). This is simpler than nxn and can be a good learning exercise, but beating cuBLAS for GEMM is hard. Still, for specific small shapes it can work.

4) Risks and constraints

- Changing the order of operations (e.g., moving ReLU6 before or after BN) would change numerics. We must preserve the original sequence: conv -> BN -> ReLU6.
- BatchNorm in training mode uses per-batch statistics and running stats; fusing or altering that is complex. In eval mode, BN is a pure elementwise affine transform and is easy to fuse.
- If we implement only elementwise parts in Triton, we won’t get large speedups over cuDNN; but it’s safe and correct.
- Implementing only the 1x1s in Triton and leaving depthwise to cuDNN is a middle ground, but then the “Triton version” does less than claimed.
